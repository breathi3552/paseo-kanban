# 将任务提示词单向发送至新 Agent

## 状态

已接受当前交付边界。2026-10-20，需求提出者已明确直接发送、单个宿主 Agent 预设下拉框、新建工作区自动使用任务标题命名，以及提交顺序和限定的异常处理，并要求通过 `to-spec` 发布规格，现已写入 [Issue #14 评论](https://github.com/breathi3552/paseo-kanban/issues/14#issuecomment-6283668277)。Git 分支名初值和 Agent 聊天标题两项默认值仍保持开放，见 [Issue #14 设计记录](../design/issue-14-solve-with-agent.md)。已实现卡片发送入口、弹窗及公开 SDK 提交流程；自动化验证通过，真实宿主验收尚待按开发指南执行。

## 背景

[Issue #14](https://github.com/breathi3552/paseo-kanban/issues/14) 希望从任务发起 Agent 协作。初期讨论采用输入框预填，但 SDK 没有公开的草稿接入点。后续需求提出者选择直接发送任务提示词并启动新 Agent，保留单向交付边界。

## 决策

- 看板负责组织任务提示词，在用户确认后直接作为初始消息发送并启动新 Agent，然后打开其聊天窗口。
- 用户先在弹窗选择已有工作区或新建工作区，并从宿主配置的 Agent 预设中选择一套配置，再执行最终提交。仅提供一个预设下拉框，不分别编辑 Provider、模型或 thinking 等参数。
- Agent 预设由 Paseo 设置拥有和维护，看板通过 `paseo.config.get()` 读取 `agentProfiles` 并应用，不建立独立预设库或预设编辑器。
- 默认选中宿主预设列表的第一项，沿用其排列顺序，不增加上次选择的持久偏好。预设选择区域保留一条说明管理位置的静态提示，不提供设置跳转按钮。
- 用户已确认宿主没有预设时禁止表单输入及发送，保留提示与关闭入口；不据此增加其他异常处理。
- 每次传递始终新建 Agent 会话，不复用已有会话。
- 默认从任务关联项目选择工作区；手动创建的任务允许用户主动切换项目，并在点击最终“传递”时保存任务自身的项目归属变更，选择过程中不立即保存。
- GitHub 导入任务不允许改绑项目，仅选择原所属项目的工作区，继续遵循 ADR-0006。
- 仅在卡片提供一个传递图标，任务详情不增加入口。
- 工作区选择合并为一个下拉框，包含已有工作区、新建普通工作区及新建 worktree，默认新建普通工作区。非 Git 项目不提供新建 worktree。
- 新建普通工作区和新建 worktree 均直接以任务标题作为名称，页面不显示新建名称字段；使用创建接口顶层 `title` 传入，已有工作区保留原名称。
- 新建 worktree 时显示独立的 Git 分支名输入框；Git 分支名由用户填写、与工作区显示名称独立，未填或不合法时就地提示并阻止发送。worktree 起点沿用 Paseo 默认分支解析。
- 用户已确认提交必填项校验，以及“保存项目变更 → 按需创建工作区 → 新建并启动 Agent”的顺序。任一步返回失败就停止本次流程，用宿主错误 Toast 反馈并保留输入；此前成功的操作不自动回滚，不自动重试。
- 原先“只预填、不提交消息”的边界被本轮明确确认的直接发送方案取代。
- 首版采用单向交付边界，不引入 Agent 运行状态向任务的回流。

## 后果与取舍

- 最终提交会启动 Agent 执行任务，不再经过宿主输入框的手动发送步骤。
- 首版不需要设计 Agent 执行状态与任务完成状态的同步映射，任务完成继续遵循 [ADR-0005](./0005-completion-lane-and-task-restoration.md)。
- 当前 SDK 0.11.4 已有工作区管理、携带初始 Prompt 创建 Agent、Provider / 模型查询及打开会话的能力；直接发送不再依赖宿主输入框预填接口。
- 始终新建会话避免混入既有会话上下文；预设读取使用宿主公开配置接口，下拉选择控件由插件绘制。
- 静态提示替代设置跳转后，首版不再依赖新增宿主设置导航接口。
- 看板原先仅关联项目、不绑定工作区的模型继续成立；项目变更只在点击最终“传递”时提交，取消选择不提交项目变更。
- ADR-0006 的 GitHub 导入任务项目锁定及按项目、Issue 编号去重规则继续成立，不需要新增导入来源身份。
- 跨看板保存和 Paseo 创建没有合并事务。用户接受上述分阶段执行与最小失败反馈，不引入自动补偿或自动重试。
- 需求提出者禁止私自增加额外异常场景处理。仅实现其明确确认的无预设、输入校验及分阶段失败反馈；如认为需要增加，须先说明必要性并询问，明确确认后再实现。
