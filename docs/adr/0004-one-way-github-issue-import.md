# 项目仓库的 GitHub Issue 单向导入

## 状态

已实施。

## 背景

为了减少在看板中重复录入需求，系统支持将项目对应的 GitHub Issues 批量导入为看板任务。设计核心在于界定数据归属、同步边界与来源范围：是一次性单向快照导入，还是双向持续状态联动？

## 决策

### 1. 单向快照复制，不作双向同步

- Issue 导入为一次性的单向数据复制。导入后的任务成为看板内的独立实体，后续编辑、状态流转（完成、恢复）或删除均不回写 GitHub。
- GitHub 上 Issue 的后续修改、关闭或评论也不会自动反向同步至看板任务。

### 2. 来源与鉴权边界

- **单一仓库绑定**：每个 Paseo 项目的导入来源严格限定为其代码目录的 Git remote `origin` 对应的 GitHub 仓库，不提供跨仓库导入，也不自动回退至 `upstream`。
- **复用守护进程凭据**：通过运行 Paseo daemon 的机器本地已认证的 `gh` CLI 登录态读取仓库，支持公开仓库以及有权访问的私有仓库。

### 3. 数据映射与实体扩展

- **字段映射**：Issue 标题复制为任务标题，正文复制为任务描述，子步骤初始为空。导入时在正文末尾以普通文本追加 Issue 编号、作者与创建时间快照。
- **内部属性**：任务实体扩展 `source`（值为 `github_issue`）、`issueNumber` 与 `externalUrl`。这些字段作为内部属性管理，用于右键菜单外链跳转与导入去重，不作为可编辑表单项。
- **项目强绑定**：从 GitHub 导入的任务，其关联项目永久锁定为导入时对应的 Paseo 项目，禁止在任务详情中改绑。

### 4. 去重与分页模型

- **去重判定**：以当前看板中的“项目 ID + Issue 编号”联合判定。已导入的 Issue 在列表中置灰且不可选；已完成的任务同样参与去重；若任务被删除，则允许再次导入（不维护永久导入历史墓碑）。
- **分页与排序**：只拉取 Open 状态的 Issues。按全仓库 Issue 创建时间排序，采用每页 25 条的标准分页，单次导入上限为 25 项。

## 后果与取舍

- **免除并发冲突**：单向导入避免了复杂的双向状态机映射、冲突合并协议及网络回写失败补偿。
- **去重局限**：去重依据是项目 ID 与 Issue 编号。若项目本地更改了 Git `origin` 仓库，编号相同的历史任务仍会阻止新仓库同编号 Issue 的导入。
