# 拖拽生命周期收敛、无锚点排序与保守并发控制

在 ADR-0001 的基础上，进一步明确任务排序在无可见锚点时的落位规则、同泳道原位不写入约定、拖拽全生命周期状态机及基于基准锁定的保守并发控制策略。

## 背景

在看板交互加深过程中，多项边界行为需要明确的领域规范：

1. **项目筛选下的排序落点**：当目标泳道不存在可见任务，但存在属于其他项目的隐藏任务时，需要明确被拖任务在该泳道所有任务中的相对插入位置。
2. **同泳道仅自身可见**：筛选状态下，当用户在同泳道内拖动唯一可见卡片并在原地或唯一有效槽位释放时，不应产生无效的网络或持久化写入，亦不应因相对锚点缺失而扰动隐藏任务的次序。
3. **拖拽与动画生命周期**：手势抓起、悬停、边缘滚动、落位动画与持久化保存属于同一交互事务，需避免控制器与 UI 表现层各自维护分裂的状态。
4. **并发控制策略**：并发会话或外部更新发生时，拖拽事务应采取保守策略，不进行基于未确认启发式规则的自动重放或静默覆盖。

## 决策

1. **无可见锚点相对追加规则**：
   - 跨泳道移动任务时，如果目标泳道在当前项目筛选下没有可见邻居（即移除被拖任务后可见任务数为 0），但该泳道在完整数据中包含属于其他项目的隐藏任务，则将该任务追加至目标泳道现有全部任务的末尾。
   - 完全没有任何任务（包括隐藏任务）的目标泳道，沿用既有的首尾夹取与数组插入逻辑。

2. **同泳道仅自身可见原位不写入（No-Op）**：
   - 当任务在原泳道内且当前筛选下该泳道只有该任务自身可见时，唯一可见槽位即代表原位。释放至该槽位判定为未变更（No-Op），不触发持久化提交，严格保持其与该泳道隐藏任务的相对次序不变。

3. **拖拽事务基准冻结（Transaction Baseline Locking）**：
   - 拖拽手势激活时，立即从同一时点捕获看板数据（`board`）、版本号（`revision`）和项目筛选状态（`selectedProjectId`），形成不可变的本次排序事务基准。
   - 从手势激活、落位动画到持久化保存结束期间，看板禁用筛选切换与本地会话替换。
   - 动画完成时，使用冻结的目标泳道、插入索引及原始基准版本号发起原子提交。

4. **保守并发与失效处理（Pessimistic Concurrency）**：
   - 看板采用乐观锁/版本号校验机制（依赖宿主 `save(board, revision)`）。
   - 拖拽与编辑均不采用自动合并或模糊锚点重放策略；当宿主因版本不匹配返回 `false` 或抛出异常时，明确报告保存失败并保持或恢复已持久化展示，提示用户刷新最新数据后重试。
   - 保存失败或异常不得阻塞拖拽生命周期解锁，确保用户在任何异常后均能继续正常交互。
